## Current State

The scvi-tools ResolVI graph dataloader work has been ported into this `scviva-tools` checkout.

Implemented behavior:

- `scviva.dataloaders.GraphDataLoader` yields `torch_geometric.data.Data` batches.
- `scviva.dataloaders.GraphDataSplitter` returns graph train/validation/test dataloaders.
- `scviva.model.ResolVI` now defaults to `GraphDataSplitter`.
- `ResolVI.train()` supports graph-scoped neighbor expression cache settings:
  - `cache_neighbor_expression: bool | Literal["auto"] = "auto"`
  - `neighbor_expression_cache_max_bytes: int | None = 1_000_000_000`
- In graph cache mode, `datasplitter_kwargs["load_neighbor_expression"]` defaults to `False`, so
  batches omit `x_n` and the module gathers neighbor expression from the dense model-side cache.
- `RESOLVAEModel._get_fn_args_from_batch()` supports three paths:
  1. model-side cache gather from `index_neighbor`;
  2. prefetched graph batch `x_n`;
  3. legacy `AnnTorchDataset` fallback.
- Sparse `x` and sparse `x_n` are still densified inside the ResolVI module, preserving legacy
  module semantics.

## Known Caveats

- `torch-geometric` remains optional, but `ResolVI` now defaults to graph dataloading. Training
  default `ResolVI` without PyG installed will fail with the `GraphDataLoader` install hint. Use
  `pip install "scviva-tools[spatial]"` or force a legacy subclass with `scvi.dataloaders.DataSplitter`.
- Cross-split neighbor expression remains intentional and matches upstream ResolVI behavior.
- The dense neighbor expression cache is a plain runtime attribute. It is not saved in checkpoints.
- The cache is guarded by estimated dense float32 expression size in `"auto"` mode.
- Benchmark-marked tests are registered but are not skipped automatically by `pyproject.toml`.
- Only the ResolVI graph port was implemented in this pass. Stage 2 still needs model-by-model
  analysis for SCVIVA, DestVI, Stereoscope, and GIMVI.

## Stage 2 Next Work

Evaluate graph dataloading for:

- `src/scviva/model/_scviva.py`
- `src/scviva/model/_destvi.py`
- `src/scviva/external/stereoscope/_model.py`
- `src/scviva/model/_gimvi.py`

Do not blindly set `_data_splitter_cls = GraphDataSplitter`. First inspect each model's
`setup_anndata()`, module `_get_fn_args_from_batch()` or equivalent batch consumption, and whether
it uses fixed per-observation neighbor arrays compatible with `index_neighbor` and
`distance_neighbor`.

Likely decision points:

- `SCVIVA`: probably applicable if its module consumes fixed neighborhood expression/context.
- `DestVI`: likely not directly applicable unless there is a fixed spatial-neighbor batch contract.
- `Stereoscope`: likely not directly applicable; it is a deconvolution model, not a neighbor graph
  model.
- `GIMVI`: requires separate analysis because it joins paired modalities and may not follow the
  same one-AnnData neighbor-index contract.
